# 罚款钱包功能设计

## 1. 背景与目标

现有“老婆卡牌管理系统”通过积分和六级卡牌记录普通错误。新增“罚款钱包”用于记录较严重错误产生的现金罚款。

本功能是夫妻之间的本地记账工具，只记录已经确认支付的罚款，不接入微信、支付宝、银行卡或其他真实支付渠道。

目标：

- 提供独立、清晰的现金罚款入口。
- 每次提交即视为已经支付，并计入累计罚款。
- 罚款与卡片积分完全独立，不互相兑换或抵扣。
- 保留现有手机中的积分、卡片历史和使用习惯。
- 将罚款数据纳入导出、导入与清空流程。

## 2. 已确认的业务规则

1. 罚款采用独立入口，不嵌入“新增错误”页面。
2. 提交罚款即视为已经支付，不设置“待支付”状态。
3. 钱包只统计累计罚款，不支持支出、提现、消费或一键清零。
4. 金额只支持人民币整数元，最小金额为 1 元。
5. 罚款不改变 `total_points`，也不生成、消耗或拆解任何卡片。
6. 钱包页面显示罚款明细；总历史页面同时展示卡片与罚款事件。
7. 首页不增加钱包模块，以维持 iPhone 16 一屏展示。

## 3. 信息架构

### 3.1 底部导航

底部导航调整为五项：

`首页｜新增｜消耗｜钱包｜历史`

数据备份继续保留在顶部右侧入口，不加入底部导航。

### 3.2 罚款钱包页面

页面从上到下包含三个区域：

1. 钱包总览卡片
   - 标题：`累计罚款`
   - 主金额：`¥1,280`
   - 次要信息：`共记录 6 次`
   - 不使用“余额”字样，避免让用户误以为系统管理支出或真实账户余额。
2. “记一笔罚款”表单
   - 日期时间：默认当前本地时间，可修改。
   - 错误类型：沿用现有六类——陪伴问题、沟通问题、承诺未完成、生活责任、态度问题、其他。
   - 错误描述：必填，最多 500 字。
   - 罚款金额：必填，人民币整数元，使用手机数字键盘。
   - 提交按钮：金额有效时显示 `确认罚款 ¥100`，无效时禁用。
3. 最近罚款明细
   - 按时间倒序显示。
   - 每条显示时间、错误类型、描述、本次金额与入账后的累计罚款。

### 3.3 提交流程

1. 用户填写表单。
2. 系统即时校验日期、描述和金额。
3. 点击提交后弹出确认框：
   - 标题：`确认记录罚款？`
   - 内容：`确认因【错误类型】罚款 ¥100？记录后将计入累计罚款。`
4. 用户取消时保留全部表单内容。
5. 用户确认后保存数据。
6. 只有保存成功后才清空表单、刷新钱包和历史，并显示成功提示。

## 4. 历史记录设计

### 4.1 钱包内明细

钱包页面仅显示罚款事件，方便快速核对现金处罚。

### 4.2 总历史

总历史将卡片记录与罚款记录合并后，按照时间倒序排列。

罚款记录使用独立视觉：

- 徽章：`现金罚款`
- 标题：错误类型
- 描述：错误描述
- 金额：`+¥100`
- 累计：`累计 ¥1,280`

罚款记录不显示卡片变化或积分变化。

卡片记录的现有样式与内容保持不变。

## 5. 数据模型

### 5.1 顶层状态

备份与本地数据版本升级为 `version: 2`：

```json
{
  "version": 2,
  "total_points": 37,
  "history": [],
  "fine_wallet": {
    "total_yuan": 1280,
    "history": []
  }
}
```

字段职责：

- `total_points`：现有卡片总积分。
- `history`：现有卡片增加与消耗记录。
- `fine_wallet.total_yuan`：累计罚款整数元。
- `fine_wallet.history`：罚款明细。

卡片历史与罚款历史分开保存，展示总历史时再按时间合并。这样可以保持现有卡片逻辑边界清晰，避免罚款记录被迫携带 `cardKey` 等无关字段。

### 5.2 罚款记录

```json
{
  "id": "fine-unique-id",
  "timestamp": "2026-07-27T10:30:00.000Z",
  "errorType": "态度问题",
  "description": "严重争吵后没有及时道歉",
  "amountYuan": 500,
  "totalAfter": 1280
}
```

约束：

- `id` 必须存在并限制长度。
- `timestamp` 必须可解析为有效时间。
- `errorType` 必须是允许的类型之一。
- `description` 去除首尾空格后不能为空，最长 500 字。
- `amountYuan` 必须是大于等于 1 的安全整数。
- `totalAfter` 必须是非负安全整数。
- 罚款历史最多 10,000 条，与现有历史安全限制一致。

### 5.3 一致性规则

`fine_wallet.history` 是累计罚款的最终依据。

读取或导入数据时，系统按照罚款历史从旧到新重新计算每条记录的 `totalAfter` 和最终 `total_yuan`。如果备份中的累计字段与明细求和不一致，以重新计算结果为准。

提交新罚款时，先计算并验证新累计金额；只有完整状态通过校验后，才一次性写入 LocalStorage。

## 6. 版本迁移与备份

### 6.1 旧数据自动升级

读取现有 `version: 1` 数据时，转换为：

```json
{
  "version": 2,
  "total_points": "保留原值",
  "history": "保留原记录",
  "fine_wallet": {
    "total_yuan": 0,
    "history": []
  }
}
```

升级不得修改积分、卡片历史或卡片换算结果。

### 6.2 导出

导出文件包含：

- 导出时间。
- 当前积分。
- 卡片历史。
- 累计罚款。
- 罚款明细。

### 6.3 导入

- 支持导入版本 1：保留原卡片数据，罚款钱包初始化为 0。
- 支持导入版本 2：恢复卡片与罚款全部数据。
- 不支持的版本、损坏 JSON 或非法字段不得覆盖当前数据。
- 用户确认覆盖后才执行导入。

### 6.4 清空数据

“清空全部数据”的确认文案明确说明将删除：

- 当前积分。
- 卡片历史。
- 累计罚款。
- 罚款明细。

仍使用二次确认，取消时不改变任何数据。

## 7. 校验与异常处理

### 7.1 表单校验

以下情况禁止提交：

- 金额为空、为 0、为负数或包含小数。
- 金额不是安全整数，或累计后超出 JavaScript 安全整数范围。
- 日期时间无效。
- 错误描述为空。

错误提示靠近当前操作，并将焦点移至需要修正的字段。

### 7.2 保存失败

LocalStorage 写入异常时：

- 不清空表单。
- 不更新页面上的累计金额。
- 显示“保存失败”提示。
- 保留写入前的内存状态。

### 7.3 导入失败

备份校验失败时：

- 不覆盖当前数据。
- 显示具体可理解的错误原因。
- 不部分恢复某一类数据。

## 8. 视觉与交互

- 继续使用现有温馨、情侣、游戏化的视觉语言。
- 钱包主卡使用香槟金、玫瑰粉和深红色，搭配硬币、爱心与轻微高光。
- 主金额为页面最强视觉层级，记录次数为次要信息。
- 所有主要按钮满足手机单手点击尺寸。
- 金额使用等宽数字特性，避免数字变化时页面跳动。
- 支持 iPhone 安全区、安卓浏览器和减少动态效果设置。
- 首页布局不增加内容，继续满足 iPhone 16 一屏显示目标。

## 9. 测试与验收标准

### 9.1 核心行为

- 记录 1 元、100 元和多笔罚款后，累计金额准确。
- 提交罚款不改变 `total_points` 和卡片数量。
- 取消确认弹窗不会保存，也不会清空表单。
- 保存成功后钱包总览、钱包明细和总历史同时更新。
- 总历史中卡片和罚款事件按真实时间倒序排列。

### 9.2 非法输入

- 拒绝空值、0、负数、小数、非数字和超大金额。
- 拒绝无效日期和空描述。
- 连续快速点击不能生成重复记录。

### 9.3 数据兼容

- 版本 1 本地数据自动升级且卡片结果不变。
- 版本 1 备份可导入。
- 版本 2 导出后再导入，积分、两类历史和累计罚款完全一致。
- 累计字段与明细不一致时，系统按照明细自动纠正。
- 损坏备份不会覆盖当前数据。

### 9.4 现有功能回归

- 新增错误、增加卡片、消耗卡片和自动拆卡行为保持正确。
- 现有卡片历史显示不变。
- 数据清空和二次确认仍有效。
- 首页在 iPhone 16 目标尺寸内保持一屏展示。
- GitHub Pages 更新后，同一浏览器来源下的旧 LocalStorage 数据能够保留并升级。

## 10. 明确不做

本阶段不包含：

- 微信、支付宝、银行卡真实扣款。
- 待支付、催缴或逾期状态。
- 钱包支出、提现、消费或退款。
- 罚款与卡片积分互换。
- 多用户、登录、云同步或跨设备自动同步。
- 单条罚款编辑或删除。
